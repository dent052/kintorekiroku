# 筋トレ記録アプリ 設計書 v2（改訂）

日付: 2026-10-19 / 状態: 承認待ち
前提: `2026-10-19-kintore-design.md`（v1）。**この文書に書いたことが v1 より優先**。書いていないことは v1 のまま。

## 1. なぜ改訂するか（利用者の実使用フィードバック）

1. 押すところが画面の上にあって押しづらい
2. 回数の目標（min〜max）は意味がない。筋トレは限界までやるもの
3. どこを押せばいいか分かりにくい
4. 黒ベースは押したくならない
5. もっと「もう1回」やりたくなる中毒性が欲しい（スプラトゥーンのガチマッチ、Twitter のタイムラインにハマった）。ただし見た目の真似ではなく、仕組みを一般化して筋トレに合わせること

## 2. 仕組みの一般化（決定の根拠）

| 元の体験 | 効いている仕組み | 筋トレでの扱い |
|---|---|---|
| ガチマッチ | 結果が分からない勝負に、短い時間で答えが返る。負けても原因が明確で「次こそ」と思える | 採用。ただし限界までやった後に即再挑戦はできないので、**届かなかった分は次回に持ち越す**。毎セットの勝敗判定はしない（体調の波で負けが続くと離脱する） |
| タイムライン | 開くたびに新しい情報があるかもしれない | 採用。ただし**本当に新しい情報があるときだけ**出す。水増ししない。読み終わったら終わる |

成功の基準は起動回数ではなく、**疲れや中断の後にも、嫌にならず戻ってこられること**。

## 3. 「ライン」— 中心の仕組み

各種目の **1セット目** にだけラインを引く（疲労の影響が最も少なく、回をまたいで比べられるため）。

### 3.1 用語
- **1セット目の値**：その回のその種目で最初に記録したセットの値（reps、time は sec）
- **今の負荷**：その種目の、今日より前の最新の非 light session の1セット目の負荷（band の order / kg / なし=0）
- **履歴 H**：今日より前・light=false の session のうち、1セット目の負荷が今の負荷と同じものの1セット目の値。新しい順に最大3件

### 3.2 ラインの決め方 `line(data, exerciseId, today)`
上から順に最初に当てはまるもの：
1. その種目の記録がない、または H が空 → `{kind:"base"}`（初回。この1セットが基準になる）
2. **負荷アップ**：最新の1セット目の値が **20回以上**（time は **60秒以上**）で、次がある（`nextId` あり／より強いバンドあり／type=weight）→ `{kind:"up", next}`。`next` は次の段階の種目名・1段強いバンド名・`{kg+1}kg`
3. **横ばい**：同じ負荷の1セット目の値が6件以上あり、新しい3件の最大 ≤ その前の3件の最大 → `{kind:"flat", value}`（ラインは 4 と同じ計算で出す）
4. **下降**：H が3件で、新しい順に h1 < h2 < h3 → `{kind:"down", value}`（ラインは出すが文言で軽めを勧める）
5. 通常 → `{kind:"line", value}`

ラインの値 = H の中央値 + 1（time は +5秒）。H が2件なら大きい方 + 1、1件ならその値 + 1。
→ 最近の実力の真ん中より少し上なので、届くかどうかが五分五分になる。

### 3.3 結果 `lineResult(line, firstValue)`
- `base` → `{kind:"base"}`
- `up` → `{kind:"newload"}`（新しい負荷の基準づくり。比較しない）
- それ以外：`firstValue >= value` → `{kind:"clear"}`、未満 → `{kind:"short", diff: value - firstValue}`

### 3.4 前回値の自動入力 `prefill`
v1 §5.2 の min/max を使う部分を置き換え：
- 記録なし：reps 10 / sec 30 / kg 5 / 最弱バンド
- `up` のとき：band は1段強いバンド、weight は kg+1、`nextId` は前回の値のまま（種目は利用者が切り替える）
- それ以外：前回の値のまま

### 3.5 文言（確定。これ以外の言い回しにしない）
| 場面 | 表示 |
|---|---|
| ラインのチップ | `ライン 16` / `ライン 45秒` |
| base（セット前） | `初回。この1セットが基準になる` |
| up（セット前） | `20回を超えた。次は{next}で。`（time は `60秒を超えた。次は{next}で。`） |
| flat（セット前） | `3回、横ばい。負荷を変えるか、1日休むタイミング` |
| down（セット前） | `下がり続けている。今日は軽めでいい` |
| clear（結果） | 大きな数字 `16`、その下に `突破`、小さく `次のライン 17` |
| short（結果） | 大きな数字 `15`、その下に `あと1`、小さく `ラインは次回へ` |
| newload（結果） | 大きな数字 `12`、その下に `新しい基準`、小さく `黒の1本目` |
| base（結果） | 大きな数字 `12`、その下に `基準` |

結果はトレーニング画面下部のカードに表示し、2.5秒後または次の操作で消す。全画面の演出はしない。clear のときだけ短いバイブ `navigator.vibrate(60)`。
「次のライン」は、今日の値を履歴に加えた上で 3.2 を計算し直した値。

## 4. 変更点（v1 からの差分）

### 4.1 削除
- 種目の目標 `min` / `max`（設定画面・データ・判定・コーチ手順から）。既存データに残っていても無視する
- `settings.weeklyGoal` と「継続 N週」、`weekStats` の `goal` / `achieved` / `streak`
- 「風邪の週だけ継続を保護」ルール
- v1 §5.1 の advice（ライン §3 に置き換え）
- 成長だけを見せる演出（v1 改修で入れた「増えたときだけ表示」）。下がった数字も**中立色**で正直に表示する

### 4.2 追加
- **通算トレーニング日数**：session がある日付の数。減らない
- **ホーム＝新着**（§5）
- **持ち越し**：前回 short だった種目のライン一覧

### 4.3 見た目
- 白ベース × オレンジ（`docs/mockup-v2.html` の案1）。トークン：
  `--bg #F5F6F8` `--surface #FFFFFF` `--fg #111827` `--fg2 #4B5563` `--line #D9DEE5` `--btn #E9ECF1` `--primary #C2410C` `--primary-d #9A3412` `--on #FFFFFF` `--good #15803D` `--good-bg #DCFCE7` `--tip #FFF1E6` `--tip-fg #9A3412` `--danger #B91C1C`
- 中立色（下がった数字など）は `--fg2`。赤では出さない
- **押すものはすべて画面下部の固定ドック**に置く（ホーム・トレーニング・履歴・設定の編集画面）。上部は表示専用
- 押せるものは必ずボタンの形：塗り（主）またはふち付き（副）、下に2〜3pxの影。押せない表示は枠も影も付けない
- 数字は Barlow Condensed のまま

### 4.4 トレーニング画面（1種目ずつ）
- 画面に出す種目は1つだけ。上から：種目名・「n / m 種目」、セット前のチップ（§3.5）、今日のセット（済みのセットを小さなチップで並べる。例 `黒 15` `黒 13`）、休憩タイマー（帯）、band の場合はバンド選択
- ドック：`− 値 ＋`（ボタン 72px）、`完了`（64px、塗り）、`◀ 前の種目` `次の種目 ▶`
- 最後の種目で `次の種目 ▶` の代わりに `終了`
- `種目を追加`・`セットを追加`・メモ・`次の段階へ切り替え` は、種目名の右の `…` から開くシートに入れる
- 休憩タイマーは帯の中に `+15秒` `スキップ`

### 4.5 終了時のまとめ
- 見出し `今日の記録`、`ライン突破 2 / 3`（clear の数 / ラインがあった種目数。base・newload は数えない）
- 合計回数と前回差。差は符号付きで、増えたら `--good`、減ったら中立色
- 出来事（v1 の sessionEvents）をそのまま並べる
- ボタン `ホームへ`

## 5. ホーム＝新着（Twitter 要素）

### 5.1 一般化（決定の根拠。Codex と2往復議論して決定）
Twitter が開かせる力は、(a) 開くたびに新しいことがあるかもしれない、(b) 大半は普通だがときどき刺さる、(c) 自分に誰かが返事をくれる、(d) 自分が何もしなくても他者の活動で補充される、(e) 確認の手間がほぼゼロ、の重なり。
v1 の新着は自分の記録からしか作れず、**休んでいる日・フェードアウト中（いちばん開く理由が必要なとき）に空になる**。そこで、自分の記録とは別に補充される「コーチ便」を加える。
ただし狙う「当たり」は褒め言葉ではなく、**自分では気づかなかった見方が1つ増えること**。同じデータの言い換え、日付付きの達成予測、催促、「久しぶり」は出さない（精度の演出・罪悪感・水増しになるため）。

### 5.2 ホームの構成
1. 見出し行：`通算 48日` と `今週 2日`（月〜日の7マス）
2. **新着**：アプリが記録から作る項目（§5.3）とコーチ便（§5.4）を**時刻の新しい順**に混ぜ、未読の「返信」は先頭に固定。表示は最大3件、その下に `すべて見る`（全件を時刻順に一覧するシート）。0件なら `新着なし`
3. **次回の候補**：short のまま残っているライン（v1 の「持ち越し」を改名。借金に見せないため）
4. ドック：`始める`（塗り）、`軽めの日`、`今日は休む`、`体重を記録`

既読：画面に表示された項目の id を `kintore:seen`（最大500件）に保存。ホームのタブに未読数のバッジ（9超は `9+`）。**フェードアウト中も未読バッジは最大2**（それ以上は積まない）。

### 5.3 アプリが記録から作る項目 `feed(data, today)`
各項目 `{id, at, kind, text}`。`at` は根拠となる session の日付、`id` は内容で一意。
| kind | 条件 | 文言 |
|---|---|---|
| `clear` | 直近の session で clear した種目 | `{種目} ライン{値}を突破` |
| `pr` / `load` / `stage` | 直近の session の sessionEvents | v1 の文言 |
| `near` | 累計が次の節目（100, 500, 1000, 以降1000刻み）まで 10% 以内 | `累計{種目} {節目}回まで あと{n}回`（time は秒） |
- 「直近の session」= 一番新しい session（今日を含む）。同じ kind が複数なら data.exercises 順で最初の1件
- v2 初版にあった `month`（1か月前比較）は削除（コーチ便の「発見」が同じ役割をより良く果たすため）

### 5.4 コーチ便（Claude の定期タスクが書く）
**ファイル**：データ用リポジトリの `posts.json`（`feedback.json` は廃止）
```json
[{ "id": "2026-10-20-reply", "at": "2026-10-20T07:31:00+09:00",
   "kind": "reply",  // reply | weekly | finding | reading
   "quote": "今日は肩が重かった",      // reply のみ：引用したメモ
   "ref": ["s_abcd1234"],             // reply のみ：返信した session の id
   "text": "本文（2〜4文）",
   "source": { "title": "…", "url": "https://…" }  // reading は必須、他は任意
}]
```
アプリは起動時とホーム表示時（10分に1回まで）に `posts.json` を取得し、`kintore:posts` に保存。新しい順に最大200件。

**メモを送る**：トレーニングのメモ欄の下に `コーチに送る` の切り替え（初期オフ）。オンのメモだけが返信の対象（session に `toCoach: true`）。毎回の助言でメモが採点される場所にならないようにするため。

**生成ルール**（`coach/README.md` に書く。1日1回 07:30 JST に実行）
1回の実行で投稿は**最大1件**。上から最初に当てはまるもの：
1. **返信**：`toCoach: true` で未返信のメモがある → 全部まとめて1件の reply。メモを引用し、要点を1つ返す。質問を返して会話の義務を作らない。データから分からない理由（疲労の原因など）を断定しない
2. **週次**（日曜のみ）：v1 §9.2 の週次レビューの内容を1件の weekly に
3. **発見**：前回の投稿以降に新しい session があり、伝える価値のある差がある → 1件の finding。事実1つとその見方。根拠の日付・種目を本文に含める
4. **読み物**：月・水・金のみ（**14日以上記録がなければ月曜のみ**）→ 1件の reading。実際に記録している種目に関係するテーマを、決めた範囲（フォームの要点、バンド・自重の負荷の上げ方、回復、限界まで追い込む理由と注意）から選ぶ。出典を付ける
5. それ以外 → 投稿しない
- 扱ったテーマ・要点・出典は `topics.json` に記録し、同じ要点を繰り返さない
- 生成に失敗しても、過去の投稿を今日の新着として再掲しない

**通知**：Claude アプリのプッシュ通知は**返信を投稿した日だけ**、要約を `コーチから返信が届きました` にする。返信がない日は要約を空に近くし（`投稿なし` / `読み物を1件`）、通知の対象にしない。
※ 定期タスクの通知が「実行のたびに届く」挙動だった場合は、最初の数日で確認して通知をオフに切り替える。

**廃止**：水曜チェック（「軽めの日だけでも」の催促）。催促はフェードアウト中の罪悪感になるため。

## 6. コーチ手順（`coach/README.md`）の変更
- §5.4 の生成ルールに全面的に書き換える
- 目標範囲 `min`〜`max` と `weeklyGoal` への言及を削除。提案は「次回のライン」と「負荷を変えるタイミング」（1セット目 20回／60秒）で書く
- 定期タスクは「毎日 07:30 のコーチ便」1本に統合（日曜の週次レビューを含む）。水曜チェックは削除

## 7. 設計者の判断で決めたこと（確認用）
- ラインは1セット目だけ。中央値 + 1（time +5秒）
- 負荷アップの目安は 20回 / 60秒（研究の目安 20〜30回の下限側。筋力の伸びと時間効率を優先）
- 勝敗・ランク・ポイント・全画面演出はしない
- 連続記録と週の目標日数は廃止、通算日数に置き換え
- 下がった数字は隠さず中立色で出す
- 新着は最大3件、本当に新しいものだけ。コーチ便は1日最大1件、返信のときだけ通知
- 日付付きの達成予測・催促・「久しぶり」は出さない
- 効果音は入れない（自宅利用。バイブのみ）
